# 质量提升与 VyOS 联动建议

本文是待实施的审查建议，不代表问题已经修复或功能已经交付。
审查基线：`a0c7c54c0cdfed21d96ee6a146fb4bf632889c05`。

## 结论与验证范围

项目已有模块化结构、权限测试、协议回归测试和跨平台 CI 基础。要达到世界级目标，建议优先保证数据可信、故障可恢复、账号安全，再扩大功能和规模。

在 Linux Docker / Go 1.27.3 下，`go test ./...`、`go vet ./...`，以及 collector、decode、pipeline、store、api 的竞态测试通过。该工具链不同于项目声明的 go1.26.9；结果不替代声明工具链验证、真实 VyOS 联调或生产负载测试。

另外两个隔离的审查测试复现了 sFlow 边界问题：expanded source index 的 `1` 与 `0x01000001` 被压缩成同一个 SourceID；零长度 counter sample 没有返回错误。其余问题为静态审查发现，未做故障注入或应用级复现。

## 十项改进建议

### 1. 写入失败可恢复（优先）

`internal/pipeline/pipeline.go:207–218,249–259` 在数据库写入前移除待写批次，失败后没有恢复路径。
建议保留未提交批次，采用有界重试与明确的事务或幂等边界，避免明细和汇总分叉。
**验收：**模拟写入中途失败，恢复后不丢失、不重复，相关汇总一致。

### 2. 时间序列和采样率保持准确（优先）

`internal/decode/nf/totals.go:32–34,58–82` 的累计转增量状态不记录上次结束时间；结合 `fields.go:495–509` 和 pipeline 的时间分摊，新流量可能被摊回旧时间段。
此外，`fields.go:467–475`、`decoder.go:332–335` 的地址级采样率借用需要检查跨 observation domain 冲突。
**验收：**长连接连续上报的分钟桶准确；不同域采样率冲突时不猜测倍率；覆盖乱序和重启。

### 3. 补齐 sFlow 协议边界（优先）

`internal/decode/sflow/sflow.go:140–145` 截断 expanded source index；`305–347` 未完整拒绝截断的 counter sample。两项均已用隔离测试复现。
建议完整保存数据源类型与索引，统一长度校验，并增加 fuzz 和真实设备报文回归。
**验收：**不同 expanded 数据源不碰撞；截断数据明确报错；合法流量不回归。

### 4. 统一密码更新与会话撤销（优先）

`internal/api/accounts.go:141–173` 的管理员重置密码路径没有像用户自行改密一样撤销已有会话。
`internal/auth/auth.go:103–154` 的账号文件读改写还需要处理并发更新与固定临时文件竞争。
**验收：**管理员重置后目标账号旧会话失效；并发账号变更不丢失；CLI 与服务的操作边界明确。

### 5. 将删分支操作移出发布流程（优先）

`.github/workflows/ci.yml:259–274` 在手动运行时独立清理分支，未检查是否已合并；开放 PR 列表未分页。
建议独立维护流程，默认只预览，完整分页，并按合并状态、保留时间和保护规则筛选。
**验收：**发布不附带删分支；未合并或仍有开放 PR 的分支不会被清理。

### 6. 给采集状态设置资源预算

`internal/collector/collector.go:247–279` 限制 agent 数，但持续活跃 agent 的 subagent/source 状态仍需独立限制。
建议设置每设备与全局容量、独立过期策略，以及超限指标。
**验收：**不断变化的数据源不会导致内存持续增长；异常设备不能拖垮其他设备的采集。

### 7. 批量写入接口计数，补齐丢弃指标

`internal/pipeline/pipeline.go:115–122,169–187` 的 counter 队列满时静默丢弃，写入和维护任务共用消费循环；`internal/store/store.go:318–324` 每条 counter 都 Flush。
建议批量提交，控制维护耗时，并暴露队列深度、丢弃数和写入延迟。
**验收：**高接口数和归档期间有可复现的吞吐、延迟、内存及丢弃报告。

### 8. 防止旧请求覆盖新页面

`internal/web/static/app.js:2497–2514,2616–2622` 的成功响应需要在渲染前检查请求代次，不能仅保护错误处理。
建议引入取消请求或代次校验，并补浏览器测试。
**验收：**快速切换时间范围、接口和页面，旧响应不能覆盖当前选择。

### 9. 把质量要求变成持续门禁

保留现有测试优势，增加针对性 race、协议 fuzz、浏览器回归、故障恢复测试和固定负载基准。
修正 `internal/web/i18n_test.go:41–46` 仅比较占位符数量的检查，改为比较完整名称。
**验收：**核心数据口径、恢复能力和性能回退有可重复验证；不以测试数量代替覆盖质量。

### 10. 提取 Linux 探针子集，两个产品共享一个核心

**架构决定：vyos-sflow 是 traffic66 的 Linux 轻量探针子集，不是原生 hsflowd 包装。** 路由器端保留包采样、真实接口计数、sFlow 导出和健康状态；DuckDB、历史存储、Web/TUI、地理库与威胁分析留在 traffic66。

当前 `internal/capture/capture.go` 输出的是聚合 flow.Record，已丢掉原始包头；`internal/encode/encode.go` 主要服务模拟器，不能直接认定为生产导出器。需要先分离原始包源与聚合器，再提取生产采样/编码核心。不能从聚合记录重造包样本。

共享核心拟放在 traffic66 仓库的独立 `probe` Go 子模块，发布版本后供两个产品依赖，解决跨仓库不能直接导入 internal 包的问题，避免长期复制分叉。模块尚未实现。VyOS 配置和服务生命周期单独适配；原生 hsflowd 仅作互操作、冲突检查和性能对照。

**验收：**探针可无 CGO 构建且不链接数据库/分析模块；真实 Linux 采样→sFlow→traffic66 可对账；独立解码器验证报文；首版仅支持内核网络路径，VPP 后置。依赖编译成功不等于真实采样或 VyOS 适配已经完成。

## 建议实施顺序

1. 先处理上述数据、安全和发布风险，逐项提交小 PR，并加入对应回归测试。
2. 再补资源预算、性能基准和浏览器质量门禁。
3. 最后以一套真实 VyOS 环境完成端到端联调，再逐步扩大版本和数据平面支持范围。

不建议为了“世界级”过早引入分布式复杂度；先证明单机可靠性、容量边界和可恢复性。
